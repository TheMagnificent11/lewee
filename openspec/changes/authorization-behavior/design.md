## Context

See `proposal.md` - Why/What Changes for motivation and scope (issue #87, plan-only per issue #528).

Today's pipeline (`ApplicationConfiguration.AddPipelineBehaviors`) registers, in order: `CorrelationIdLoggingBehavior`, `TenantLoggingBehavior` (adds `TenantId` to the logging scope only - no authorization), `PerformanceBehavior`, `FailureLoggingBehavior`, `UnhandledExceptionBehavior`, `DomainExceptionBehavior`, `ValidationBehavior`. Each is an open-generic `IPipelineBehavior<,>` constrained via a marker interface (`ITenantRequest`, `ICommand`), so MediatR only invokes it for requests satisfying that constraint - the same technique this plan reuses for the two new authorization behaviors. `TenantLoggingBehavior` only makes sense for hosts using `ITenantRequest`/tenant membership (i.e. those adopting `Lewee.Auth.*`) - it was left in `Lewee.Application` when `Lewee.Auth.*` was introduced by `multi-tenancy-support`; this plan corrects that by moving it alongside the new behaviors (Decision 4).

`Lewee.Common` already defines `ResultStatus.Unauthenticated`/`Unauthorized`, and `CommandEndpoint`/`QueryEndpoint` (`Lewee.Infrastructure.FastEndpoints`) already map `Unauthenticated` → 401 and `Unauthorized` → 403. `IAuthenticatedUserService.UserId` (`Lewee.Infrastructure.Auth`) already resolves the caller's external identity (the `NameIdentifier` claim) from `HttpContext`, matching `User.ExternalId` (`Lewee.Auth.Domain`). None of this needs to change - the new behaviors are pure consumers of it.

`Lewee.Domain` already has an `IQueryProjection`/`IQueryProjectionService`/`QueryProjectionReference` read-model mechanism, implemented by `QueryProjectionService<TContext>` (`Lewee.Infrastructure.Data`) against any `ApplicationDbContext<TContext>` (including the existing `AuthDbContext`). It stores an arbitrary JSON-serialized projection keyed by a string, looked up with a single indexed-column query (`WHERE QueryProjectionAssemblyName = ... AND QueryProjectionClassName = ... AND Key = ...`, no joins) - exactly the "stored query with an appropriate key" issue #87 calls for. `sample/Pizzeria.Store.Application/Orders/OrderingDomainEventHandler.cs` + `sample/Pizzeria.Store.Domain/OrderQueryProjection.cs` is the existing, working example of a domain event handler maintaining a query projection; this plan's authorization-lookup capability follows the same pattern instead of introducing a new persistence mechanism.

`Lewee.Auth.Domain`'s `Tenant`/`User`/`TenantMembership` (from the not-yet-archived `multi-tenancy-support` change) have no concept of a site administrator or a role today. `sample/Pizzeria.Configuration/AuthSeeder.cs` currently seeds a reserved `"ADMIN"` tenant and assigns the seeded admin user to it - this was a mistake carried over from a previous PR (site administration should never have depended on tenant membership) and this plan removes it in favour of a direct `IsSiteAdministrator` flag (Decision 1).

`Lewee.Auth.Application` already references both `Lewee.Application` and `Lewee.Auth.Domain` (per its `.csproj`), and already hosts `AuthApplicationConfiguration` (registering MediatR handlers/validators for `Lewee.Auth.Application`). This plan adds the new marker interfaces and behaviors alongside it, so they can depend on `Lewee.Auth.Domain` concepts (`User.IsSiteAdministrator`, tenant roles) directly, with no new cross-layer abstraction required.

Constraints:
- `Lewee.Domain`/`Lewee.Auth.Domain` have no dependencies on other layers; the domain changes (`User.IsSiteAdministrator`, `TenantMembership` role assignment) must not reference EF Core or ASP.NET Core.
- `Lewee.Application` itself must remain usable without any dependency on `Lewee.Auth.*`; the new marker interfaces and behaviors therefore live in `Lewee.Auth.Application`, not `Lewee.Application` (Decision 4).
- Pipeline behaviors are resolved from DI as open generics constrained by marker interfaces (existing pattern); the new behaviors follow the same shape `TenantLoggingBehavior` already uses.

## Goals / Non-Goals

**Goals:**
- Let a site administrator define a global catalog of roles (e.g. Pizzeria's future "Manager"/"Store Worker"/"Delivery Driver"), and let a `User`'s `TenantMembership` be assigned zero, one, or many of them, additive to the existing `auth/tenant-management` model.
- Provide a single-key, no-join lookup of a caller's roles for a tenant, reusing the existing `IQueryProjection`/`IQueryProjectionService` mechanism rather than inventing a new one.
- Add two opt-in `MediatR` pipeline behaviors - one for site-administrator-only requests (checked directly against `User.IsSiteAdministrator`), one for tenant-role-restricted requests (checked against the request's own `TenantId` and required roles) - that short-circuit with `Unauthenticated`/`Unauthorized` `ResultStatus`es already wired to 401/403.
- Keep both behaviors, their marker interfaces, and `TenantLoggingBehavior` in `Lewee.Auth.Application`, opt-in via a new `ApplicationAuthConfiguration` class, so only applications that adopt `Lewee.Auth.*` - and specifically want these authorization behaviors - incur any dependency or registration cost.

**Non-Goals:**
- Building any UI/API for managing `IsSiteAdministrator`, defining roles, or assigning them to a tenant's members (e.g. `DefineRoleCommand`, `AssignRoleCommand`, or endpoints) - this plan only fixes the domain shape (`User.IsSiteAdministrator`, `Role`, `TenantMembership` role assignment) and the pipeline behaviors that consume it; `IsSiteAdministrator` is expected to be set directly against the database given how rarely it changes, while role definition/assignment commands and endpoints - including which caller (a site administrator defining roles, or a tenant's own manager assigning them to that tenant's members) is authorized to call each - are follow-up work.
- Retrofitting `IAdministratorRequest`/`ITenantRoleRequest` onto any existing Pizzeria command/query - that adoption is separate follow-up work under parent issue #87, not part of this plan.
- A generic, declarative "roles required" attribute/policy system beyond the two marker interfaces described here (e.g. `[RequireRole("...")]`) - out of scope; can be layered on afterward without changing the specs in this plan.
- Changing how `IAuthenticatedUserService` resolves the caller, or how `ITenantRequest` works today - both are reused as-is. `TenantLoggingBehavior`'s own logic is unchanged; only its project moves (Decision 4).

## Decisions

1. **Site-administrator authorization is a direct `IsSiteAdministrator` boolean on `User`, independent of tenant or role.**
   `User` gains an `IsSiteAdministrator` property. `IAdministratorRequest` requires only that the caller's `User.IsSiteAdministrator` is `true` - no tenant, no role, no lookup beyond resolving the caller's `User` by external ID. No application command sets this flag; there are expected to be only one or a handful of site administrators, so it is set directly against the database (e.g. a SQL `UPDATE`). As part of this decision, `sample/Pizzeria.Configuration/AuthSeeder.cs`'s reserved `"ADMIN"` tenant (and the seeded admin user's membership in it) is removed - it was a mistake from a previous PR that entangled a system-wide concept (site administrator) with the tenant/role model; the seeded admin user's `IsSiteAdministrator` is set directly instead.
   *Alternative considered*: Model site-administrator authorization as tenant-role authorization against a reserved administrative tenant (the original decision in this plan). Rejected per direct feedback: it unnecessarily reuses the tenant/role model for a concept that has nothing to do with tenants, and depends on `AuthSeeder`'s `"ADMIN"` tenant, which itself should not exist.

2. **`Role` is a global entity, defined only by a site administrator - not owned by, or defined per, `Tenant`. A `TenantMembership` can be assigned multiple roles at once.**
   `Lewee.Auth.Domain` gains a `Role` root entity (`Id`, a globally-unique `Code`, `Name`), created via `Role.Create(code, name, correlationId)` (idempotent-by-code - defining the same code twice is rejected, since codes are unique across the whole system, not per tenant) and raising a role-defined domain event. `Role` is defined once, globally, by the site administrator (e.g. a Pizzeria head-office administrator authoring "Manager"/"Store Worker"/"Delivery Driver" for every store/tenant to use) - it is not owned by, or scoped to, any single `Tenant`; every tenant in the deployment shares the same role catalog and can assign any defined `Role` to its own members. `TenantMembership` gains `AssignRole(roleId, correlationId)`/`RemoveRole(roleId, correlationId)` methods (idempotent, matching the existing `AssignToTenant`/`RemoveFromTenant` idempotency pattern) referencing that global `Role` by ID, with no per-tenant ownership or cross-tenant validation needed (any defined `Role` may be assigned to any tenant's membership). A single membership can hold zero, one, or many roles simultaneously (e.g. in a future Pizzeria sample, a tenant member could hold both "Manager" and "Delivery Driver" for the same tenant, since some apps - like a kitchen or delivery app - should be reachable by more than one role).
   *Alternative considered*: `Role` as a child entity owned by `Tenant`, individually defined by each tenant (the original decision). Rejected per direct feedback: every tenant shares the same role catalog, defined centrally by the site administrator (e.g. Pizzeria's head office), not invented independently by each tenant/store - a per-tenant catalog would let tenants define inconsistent, unrelated roles rather than the shared set the site administrator intends to offer across the whole deployment.
   *Alternative considered*: Fixed, hardcoded (compile-time) role codes, with `Lewee.Auth.Domain` not persisting any `Role` catalog at all (an intermediate revision of this decision). Rejected per direct feedback: role codes are not fixed at development time - the site administrator creates them as data, so a running deployment can be offered new roles later without a code change; `Role` must therefore be a real, persisted entity that the site administrator manages, not a compile-time constant.
   *Alternative considered*: A single role per membership (`TenantMembership.Role` as a scalar). Rejected because a membership must be able to hold more than one role concurrently (e.g. a manager needing access to both a kitchen app and a delivery app).

3. **The authorization lookup reuses the existing `IQueryProjection`/`IQueryProjectionService` mechanism, keyed by `$"{tenantId}:{externalUserId}"`.**
   A new `TenantMembershipRolesQueryProjection : IQueryProjection` (holding the assigned role codes, plus `CorrelationId`) is maintained via `IQueryProjectionService.AddOrUpdateAsync`/`RetrieveByKeyAsync` against `AuthDbContext`'s existing `QueryProjectionReferences` table, exactly like `sample/Pizzeria.Store.Domain/OrderQueryProjection.cs` + `OrderingDomainEventHandler` do for orders today. The lookup is updated by a domain event handler (in `Lewee.Auth.Application`) reacting to `TenantMembershipCreatedEvent`/`TenantMembershipRemovedEvent` (existing) and the new role-assigned/role-removed events (Decision 2), so a single indexed read (no join across `Tenants`/`Users`/`TenantMemberships`) resolves a caller's roles for a tenant at authorization time. This lookup is used only by `TenantRoleAuthorizationBehavior` - `AdministratorAuthorizationBehavior` does not need it, since `IsSiteAdministrator` (Decision 1) is not tenant-scoped.
   *Alternative considered*: A dedicated, purpose-built SQL table/view (e.g. `auth.UserTenantRoles(TenantId, ExternalId, RoleCodes)`) with its own EF configuration and repository. Rejected in favor of the existing, framework-level `IQueryProjection` mechanism: it already provides the "single key, no join" property issue #87 asks for, is proven in the sample, and avoids introducing a second read-model pattern into the framework.

4. **The two new pipeline behaviors, their marker interfaces, and `TenantLoggingBehavior` all live in `Lewee.Auth.Application`, registered opt-in via a new `ApplicationAuthConfiguration` class.**
   `IAdministratorRequest`, `ITenantRoleRequest`, `AdministratorAuthorizationBehavior<TRequest, TResponse>`, and `TenantRoleAuthorizationBehavior<TRequest, TResponse>` are all added to `Lewee.Auth.Application` (not `Lewee.Application`), since all four depend directly on `Lewee.Auth.Domain` concepts (`User.IsSiteAdministrator`, tenant roles). `TenantLoggingBehavior` moves from `Lewee.Application` to `Lewee.Auth.Application` alongside them, correcting an oversight from `multi-tenancy-support` (it already only applies to `ITenantRequest`s, which only make sense for `Lewee.Auth.*` consumers). A new `ApplicationAuthConfiguration` class in `Lewee.Auth.Application` (separate from the existing `AuthApplicationConfiguration`, which registers MediatR handlers/validators) exposes a method that registers `TenantLoggingBehavior`, `AdministratorAuthorizationBehavior`, and `TenantRoleAuthorizationBehavior` via `Lewee.Application.ApplicationConfiguration.AddPipelineBehaviors`'s existing `additionalBehaviors` parameter. This registration is opt-in and separate from `AuthApplicationConfiguration` because not every consumer of `Lewee.Auth.Application` requires these authorization/logging behaviors. Each behavior resolves the caller's identity from `IAuthenticatedUserService.UserId`; a `null`/empty ID short-circuits with `Unauthenticated` before any further check runs.
   *Alternative considered*: Keep the marker interfaces and behaviors in `Lewee.Application`, behind a new `Lewee.Application`-level abstraction (e.g. `ITenantRoleAuthorizationService`) implemented in `Lewee.Auth.Application` (the original decision). Rejected per direct feedback: since the behaviors are only ever useful to `Lewee.Auth.*` consumers, moving them (not just their implementation) into `Lewee.Auth.Application` is simpler and avoids an abstraction with a single real implementation.
   *Alternative considered*: Register the new behaviors unconditionally as part of `Lewee.Auth.Application`'s existing `AuthApplicationConfiguration`. Rejected because not every consumer of `Lewee.Auth.Application` (e.g. one only needing `Lewee.Auth.*` domain/data concepts without pipeline authorization) wants these behaviors active; a distinct, explicitly-opted-into `ApplicationAuthConfiguration` keeps the two concerns separate.

5. **Ordering: authorization runs after validation, before the handler and before performance/failure logging that assume an authorized request.**
   `AddPipelineBehaviors` registers behaviors in a fixed order matching `IPipelineBehavior` composition (first-registered wraps outermost); the two authorization behaviors slot in immediately after `ValidationBehavior` (malformed requests should fail validation before spending a lookup) and before `PerformanceBehavior`/`FailureLoggingBehavior`/`DomainExceptionBehavior`/`UnhandledExceptionBehavior` (which should only measure/log/handle exceptions for requests that were actually authorized to reach the handler). `TenantLoggingBehavior` (logging-scope only, no short-circuit) continues to run for any `ITenantRequest`, so an authorization failure is still logged with the tenant ID in scope.
   *Alternative considered*: Run authorization before validation. Rejected - an unauthorized caller sending a malformed request should still fail fast on validation without needing a lookup, and returning `BadRequest` vs `Unauthorized` first is not security-sensitive here since both are already-failure outcomes with no information disclosure beyond "this request was rejected."

## Risks / Trade-offs

- [Reusing `IQueryProjectionService`'s generic JSON-blob storage for a security-sensitive, hot-path lookup (evaluated on every authorized request) may be less performant than a dedicated indexed table once role/tenant volume grows] → Mitigate by confirming `QueryProjectionReference`'s existing `(QueryProjectionAssemblyName, QueryProjectionClassName, Key)` filter is backed by an index (verify during implementation; add one if missing) before relying on it for per-request authorization checks; if performance testing later shows this insufficient, a dedicated table is a compatible follow-up since only `TenantRoleAuthorizationBehavior`'s internals would need to change.
- [The authorization lookup can be transiently stale between a `TenantMembership`/role domain event being raised and its handler updating the projection (eventual consistency), since domain event handlers run as `INotificationHandler`s after the triggering command completes] → Acceptable per existing repo convention (the same staleness window already exists for `OrderQueryProjection`); call out in `tasks.md` that role/membership changes and the authorization check they gate are not expected to be strictly transactional.
- [Moving `TenantLoggingBehavior` out of `Lewee.Application` is a source-breaking change for any host referencing it directly from that namespace, rather than via `ApplicationConfiguration.AddPipelineBehaviors`] → Acceptable: it is not currently referenced directly outside the framework's own default registration, and the fix corrects a design mistake (it should never have lived outside `Lewee.Auth.Application`, since it only applies to `ITenantRequest`s).
- [Two new marker-interface-driven behaviors add further conditional pipeline branching, increasing the number of interfaces a request author must reason about (`ICommand`/`IQuery`, `ITenantRequest`, now `IAdministratorRequest`/`ITenantRoleRequest`)] → Acceptable and consistent with the existing `ITenantRequest` precedent; `tasks.md` includes unit tests asserting requests that don't implement either interface are unaffected (already codified as scenarios in the `application/*-authorization` specs).

## Migration Plan

1. Add `IsSiteAdministrator` to `User` (`Lewee.Auth.Domain`), defaulting to `false`, with no domain method to set it (mutated directly against the database, per Decision 1).
2. Add `Role` (`Lewee.Auth.Domain`, a root entity with a globally-unique code and a name, not owned by `Tenant`) with `Role.Create(code, name, correlationId)` (idempotent-by-code) and a role-defined domain event, plus `TenantMembership.AssignRole(roleId, correlationId)`/`RemoveRole(roleId, correlationId)` (idempotent) and role-assigned/role-removed domain events (Decision 2).
3. Add EF Core configuration/migration in `Lewee.Auth.Infrastructure.Data` for `User.IsSiteAdministrator`, the `Role` entity (unique index on `Code`), and the membership-role assignment (a join table under the `auth` schema keyed by membership + role), per `auth/role-management`.
4. Add `TenantMembershipRolesQueryProjection : IQueryProjection` (role codes + `CorrelationId`) and a domain event handler in `Lewee.Auth.Application` that keeps it in sync (via `IQueryProjectionService` against `AuthDbContext`) with `TenantMembershipCreatedEvent`/`TenantMembershipRemovedEvent` and the new role events, keyed by `$"{tenantId}:{externalUserId}"`, per `auth/authorization-lookup`.
5. Add `IAdministratorRequest`/`ITenantRoleRequest` and `AdministratorAuthorizationBehavior`/`TenantRoleAuthorizationBehavior` to `Lewee.Auth.Application`, plus `TenantLoggingBehavior` moved there from `Lewee.Application`, per `application/administrator-authorization` and `application/tenant-role-authorization`.
6. Add `ApplicationAuthConfiguration` to `Lewee.Auth.Application`, registering the three behaviors from step 5 as opt-in, additional pipeline behaviors via `ApplicationConfiguration.AddPipelineBehaviors`'s existing `additionalBehaviors` parameter (design.md Decision 5 for ordering).
7. Remove `sample/Pizzeria.Configuration/AuthSeeder.cs`'s reserved `"ADMIN"` tenant creation and the seeded admin user's assignment to it; set the seeded admin user's `IsSiteAdministrator` to `true` directly instead. No data migration is required - the sample's database is not deployed anywhere yet, so it can simply be recreated.
8. Add unit tests: `Lewee.Auth.Domain.Tests.Unit` (`IsSiteAdministrator` default/assignment, role assignment/removal, idempotency), `Lewee.Auth.Application.Tests.Unit` (projection sync, both behaviors including the "no marker interface ⇒ unaffected" and "no authenticated caller ⇒ `Unauthenticated`" scenarios from the specs, and `ApplicationAuthConfiguration`'s registration).
9. Run `dotnet build --configuration Release --nologo`, `dotnet test --filter "FullyQualifiedName!~Integration" --configuration Release --no-build --nologo`, and `dotnet format` to confirm no regressions.
10. (Deferred, tracked only) adopt `IAdministratorRequest`/`ITenantRoleRequest` on real Pizzeria commands/queries, and add role-management commands/endpoints (Non-Goals) - both are separate follow-up changes under parent issue #87.

No rollback beyond standard EF Core migration `Down()` methods is planned; this is additive (new tables/columns), so no existing data is at risk. Removing `AuthSeeder`'s `"ADMIN"` tenant creation does not require a migration, since the sample is not deployed anywhere - its database can simply be recreated.

## Open Questions

- The exact shape of the future role-management commands/endpoints - `DefineRoleCommand` (restricted to a site administrator, e.g. via `IAdministratorRequest`) and `AssignRoleCommand`/`RemoveRoleCommand` (whether restricted to a site administrator only, or also to a tenant's own manager-equivalent role via `ITenantRoleRequest`, so tenants can manage their own members' roles once a manager exists) - is deliberately left for later work (see Non-Goals); this plan only fixes the domain/lookup/pipeline shape needed to support it.
- The actual set of role codes a deployment's site administrator chooses to define (e.g. Pizzeria's planned "Manager"/"Store Worker"/"Delivery Driver" for its kitchen and delivery apps) is data, decided at runtime by that site administrator - not part of this plan's specs.
