## Context

See `proposal.md` - Why/What Changes for motivation and scope (issue #87, plan-only per issue #528).

Today's pipeline (`ApplicationConfiguration.AddPipelineBehaviors`) registers, in order: `CorrelationIdLoggingBehavior`, `TenantLoggingBehavior` (adds `TenantId` to the logging scope only - no authorization), `PerformanceBehavior`, `FailureLoggingBehavior`, `UnhandledExceptionBehavior`, `DomainExceptionBehavior`, `ValidationBehavior`. Each is an open-generic `IPipelineBehavior<,>` constrained via a marker interface (`ITenantRequest`, `ICommand`), so MediatR only invokes it for requests satisfying that constraint - the same technique this plan reuses for the two new authorization behaviors.

`Lewee.Common` already defines `ResultStatus.Unauthenticated`/`Unauthorized`, and `CommandEndpoint`/`QueryEndpoint` (`Lewee.Infrastructure.FastEndpoints`) already map `Unauthenticated` → 401 and `Unauthorized` → 403. `IAuthenticatedUserService.UserId` (`Lewee.Infrastructure.Auth`) already resolves the caller's external identity (the `NameIdentifier` claim) from `HttpContext`, matching `User.ExternalId` (`Lewee.Auth.Domain`). None of this needs to change - the new behaviors are pure consumers of it.

`Lewee.Domain` already has an `IQueryProjection`/`IQueryProjectionService`/`QueryProjectionReference` read-model mechanism, implemented by `QueryProjectionService<TContext>` (`Lewee.Infrastructure.Data`) against any `ApplicationDbContext<TContext>` (including the existing `AuthDbContext`). It stores an arbitrary JSON-serialized projection keyed by a string, looked up with a single indexed-column query (`WHERE QueryProjectionAssemblyName = ... AND QueryProjectionClassName = ... AND Key = ...`, no joins) - exactly the "stored query with an appropriate key" issue #87 calls for. `sample/Pizzeria.Store.Application/Orders/OrderingDomainEventHandler.cs` + `sample/Pizzeria.Store.Domain/OrderQueryProjection.cs` is the existing, working example of a domain event handler maintaining a query projection; this plan's authorization-lookup capability follows the same pattern instead of introducing a new persistence mechanism.

`Lewee.Auth.Domain`'s `Tenant`/`User`/`TenantMembership` (from the not-yet-archived `multi-tenancy-support` change) have no concept of a role today, and `sample/Pizzeria.Configuration/AuthSeeder.cs` already seeds a reserved `"ADMIN"` tenant code/name pair, giving this plan a concrete, existing "administrative tenant" to anchor `IAdministratorRequest` on.

Constraints:
- `Lewee.Domain`/`Lewee.Auth.Domain` have no dependencies on other layers; `Role` and the extended `TenantMembership` must not reference EF Core or ASP.NET Core.
- `Lewee.Application` depends only on `Lewee.Domain` (+ MediatR/FluentValidation/Correlate); the new pipeline behaviors must not take a compile-time dependency on `Lewee.Auth.Domain` or `Lewee.Auth.Infrastructure.Data` - they can only depend on an abstraction.
- Pipeline behaviors are resolved from DI as open generics constrained by marker interfaces (existing pattern); the new behaviors follow the same shape as `TenantLoggingBehavior`.

## Goals / Non-Goals

**Goals:**
- Give tenants a way to define roles and assign/remove them on a `User`'s `TenantMembership`, additive to the existing `auth/tenant-management` model.
- Provide a single-key, no-join lookup of a caller's roles for a tenant, reusing the existing `IQueryProjection`/`IQueryProjectionService` mechanism rather than inventing a new one.
- Add two opt-in `MediatR` pipeline behaviors - one for site-administrator-only requests (checked against the reserved `"ADMIN"` tenant), one for tenant-role-restricted requests (checked against the request's own `TenantId`) - that short-circuit with `Unauthenticated`/`Unauthorized` `ResultStatus`es already wired to 401/403.
- Keep `Lewee.Application`'s new marker interfaces/behaviors framework-agnostic of `Lewee.Auth.*`, so any Lewee-based application (not just Pizzeria) can supply its own role/authorization-lookup implementation.

**Non-Goals:**
- Building any UI/API for tenant administrators to define or assign roles (e.g. `CreateRoleCommand`, `AssignRoleCommand`, or endpoints) - this plan only fixes the domain shape (`Role`, `TenantMembership` role assignment) and the pipeline behaviors that consume it; the commands/endpoints to manage roles are follow-up work.
- Retrofitting `IAdministratorRequest`/`ITenantRoleRequest` onto any existing Pizzeria command/query - that adoption is separate follow-up work under parent issue #87, not part of this plan.
- A generic, declarative "roles required" attribute/policy system beyond the two marker interfaces described here (e.g. `[RequireRole("...")]`) - out of scope; can be layered on afterward without changing the specs in this plan.
- Changing how `IAuthenticatedUserService` resolves the caller, or how `ITenantRequest`/`TenantLoggingBehavior` work today - both are reused as-is.

## Decisions

1. **Site-administrator authorization is modeled as tenant-role authorization against a reserved administrative tenant, not a separate concept.**
   `IAdministratorRequest` and `ITenantRoleRequest` both resolve to "is this caller a member of tenant X with role Y?" - `IAdministratorRequest` fixes `X` to the reserved administrative tenant (the `"ADMIN"` tenant code already seeded by `sample/Pizzeria.Configuration/AuthSeeder.cs`) while `ITenantRoleRequest` takes `X` from `request.TenantId`. This means both pipeline behaviors, and the underlying `auth/role-management`/`auth/authorization-lookup` capabilities, are a single mechanism used two ways, rather than two parallel authorization systems.
   *Alternative considered*: A separate `IsSiteAdministrator` flag on `User`, independent of tenant membership. Rejected because it would duplicate the membership/role machinery this plan already needs for tenant-role authorization, and because the sample already treats "administrator" as membership of a reserved tenant (`AuthSeeder`), so introducing a second mechanism would contradict existing, working code.

2. **`Role` is a child entity owned by `Tenant`, with a per-tenant-unique (not globally unique) code; `TenantMembership` gains a collection of assigned roles.**
   Mirrors how `TenantMembership` is already a child entity owned by `User` (per `auth/tenant-management`): `Role` lives under `Tenant` in `Lewee.Auth.Domain`, with `Tenant.DefineRole(code, name, correlationId)` (idempotent-by-code within the tenant) raising a role-defined event, and `TenantMembership` gaining `AssignRole(roleId, correlationId)`/`RemoveRole(roleId, correlationId)` methods (idempotent, matching the existing `AssignToTenant`/`RemoveFromTenant` idempotency pattern) that validate the role belongs to the membership's own tenant before assigning it.
   *Alternative considered*: A single, fixed, globally-shared enum of roles (e.g. `enum Role { Member, Admin }`) shared across all tenants. Rejected per issue #87's explicit ask that "tenant admins can define different roles" - roles must be data, not compiled-in constants.

3. **The authorization lookup reuses the existing `IQueryProjection`/`IQueryProjectionService` mechanism, keyed by `$"{tenantId}:{externalUserId}"`.**
   A new `TenantMembershipRolesQueryProjection : IQueryProjection` (holding the assigned role codes, plus `CorrelationId`) is maintained via `IQueryProjectionService.AddOrUpdateAsync`/`RetrieveByKeyAsync` against `AuthDbContext`'s existing `QueryProjectionReferences` table, exactly like `sample/Pizzeria.Store.Domain/OrderQueryProjection.cs` + `OrderingDomainEventHandler` do for orders today. The lookup is updated by a domain event handler (in `Lewee.Auth.Application`) reacting to `TenantMembershipCreatedEvent`/`TenantMembershipRemovedEvent` (existing) and the new role-defined/assigned/removed events (Decision 2), so a single indexed read (no join across `Tenants`/`Users`/`TenantMemberships`/`Roles`) resolves a caller's roles for a tenant at authorization time.
   *Alternative considered*: A dedicated, purpose-built SQL table/view (e.g. `auth.UserTenantRoles(TenantId, ExternalId, RoleCodes)`) with its own EF configuration and repository. Rejected in favor of the existing, framework-level `IQueryProjection` mechanism: it already provides the "single key, no join" property issue #87 asks for, is proven in the sample, and avoids introducing a second read-model pattern into the framework.

4. **The two new pipeline behaviors live in `Lewee.Application` and depend only on an abstraction for the lookup, not on `Lewee.Auth.*` directly.**
   `AdministratorAuthorizationBehavior<TRequest, TResponse>` and `TenantRoleAuthorizationBehavior<TRequest, TResponse>` (in `Lewee.Application.Mediation.Behaviors`, alongside `TenantLoggingBehavior`) depend on a new `Lewee.Application`-level abstraction (e.g. `ITenantRoleAuthorizationService`, exposing an async "does this external user hold this role for this tenant ID?" check) rather than depending on `Lewee.Auth.Domain`/`IQueryProjectionService` directly - `Lewee.Auth.Application` (or the host application) supplies the implementation that queries the authorization lookup (Decision 3) and registers it in DI, following the same "framework defines the contract, a lower/host layer supplies it" shape already used for `IAuthenticatedUserService` (defined in `Lewee.Common`, implemented in `Lewee.Infrastructure.Auth`). Each behavior resolves the caller's identity from `IAuthenticatedUserService.UserId`; a `null`/empty ID short-circuits with `Unauthenticated` before the role check runs. Both behaviors are registered as additional, opt-in entries via `ApplicationConfiguration.AddPipelineBehaviors`'s existing `additionalBehaviors` parameter (used by hosts that need `Lewee.Auth.*`, e.g. `Pizzeria.Store.Api`) rather than unconditionally in the framework-wide default list, since not every Lewee-based application depends on `Lewee.Auth.*`.
   *Alternative considered*: Depend on `Lewee.Auth.Domain`/`Lewee.Auth.Infrastructure.Data` directly from `Lewee.Application`. Rejected because `Lewee.Application` is a shared framework package that must not force every consumer to take on the `Lewee.Auth.*` packages/schema just to get validation/logging/exception-handling behaviors.
   *Alternative considered*: Register the two behaviors unconditionally alongside the other default behaviors in `AddPipelineBehaviors`. Rejected for the same reason - doing so would require `ITenantRoleAuthorizationService` to always be registered, even by hosts with no `Lewee.Auth.*` dependency, which the "framework has no dependencies it doesn't need" principle (`decision-making.instructions.md`) rules out.

5. **Ordering: authorization runs after validation, before the handler and before performance/failure logging that assume an authorized request.**
   `AddPipelineBehaviors` registers behaviors in a fixed order matching `IPipelineBehavior` composition (first-registered wraps outermost); the two authorization behaviors slot in immediately after `ValidationBehavior` (malformed requests should fail validation before spending a lookup) and before `PerformanceBehavior`/`FailureLoggingBehavior`/`DomainExceptionBehavior`/`UnhandledExceptionBehavior` (which should only measure/log/handle exceptions for requests that were actually authorized to reach the handler). `TenantLoggingBehavior` (logging-scope only, no short-circuit) continues to run for any `ITenantRequest`, so an authorization failure is still logged with the tenant ID in scope.
   *Alternative considered*: Run authorization before validation. Rejected - an unauthorized caller sending a malformed request should still fail fast on validation without needing a lookup, and returning `BadRequest` vs `Unauthorized` first is not security-sensitive here since both are already-failure outcomes with no information disclosure beyond "this request was rejected."

## Risks / Trade-offs

- [Reusing `IQueryProjectionService`'s generic JSON-blob storage for a security-sensitive, hot-path lookup (evaluated on every authorized request) may be less performant than a dedicated indexed table once role/tenant volume grows] → Mitigate by confirming `QueryProjectionReference`'s existing `(QueryProjectionAssemblyName, QueryProjectionClassName, Key)` filter is backed by an index (verify during implementation; add one if missing) before relying on it for per-request authorization checks; if performance testing later shows this insufficient, a dedicated table is a compatible follow-up since the abstraction (`ITenantRoleAuthorizationService`) hides the storage choice from `Lewee.Application`.
- [The authorization lookup can be transiently stale between a `TenantMembership`/role domain event being raised and its handler updating the projection (eventual consistency), since domain event handlers run as `INotificationHandler`s after the triggering command completes] → Acceptable per existing repo convention (the same staleness window already exists for `OrderQueryProjection`); call out in `tasks.md` that role/membership changes and the authorization check they gate are not expected to be strictly transactional.
- [Making `IAdministratorRequest` depend on a hardcoded reserved tenant code (`"ADMIN"`) couples the framework-level concept of "site administrator" to a sample-specific string constant] → Mitigate by having the reserved administrative tenant code be a configurable/constant value owned by `Lewee.Auth.Domain` (e.g. promote `AuthSeeder`'s private `AdministrativeTenantCode` to a public `Tenant.AdministrativeTenantCode` constant or equivalent) rather than each host redefining its own string, so `Lewee.Auth.Application`'s `ITenantRoleAuthorizationService` implementation and `AuthSeeder` share a single source of truth.
- [Two new marker-interface-driven behaviors add further conditional pipeline branching, increasing the number of interfaces a request author must reason about (`ICommand`/`IQuery`, `ITenantRequest`, now `IAdministratorRequest`/`ITenantRoleRequest`)] → Acceptable and consistent with the existing `ITenantRequest` precedent; `tasks.md` includes unit tests asserting requests that don't implement either interface are unaffected (already codified as scenarios in the `application/*-authorization` specs).

## Migration Plan

1. Add `Role` to `Lewee.Auth.Domain` (child entity owned by `Tenant`, per-tenant-unique code), `Tenant.DefineRole(...)`, and role-defined domain event.
2. Add `TenantMembership.AssignRole(roleId, correlationId)`/`RemoveRole(roleId, correlationId)` (idempotent) plus role-assigned/role-removed domain events, validating the role's `TenantId` matches the membership's tenant.
3. Add EF Core configuration/migration in `Lewee.Auth.Infrastructure.Data` for `Role` and the membership-role assignment (owned/join table under the `auth` schema), per `auth/role-management`.
4. Add `TenantMembershipRolesQueryProjection : IQueryProjection` (role codes + `CorrelationId`) and a domain event handler in `Lewee.Auth.Application` that keeps it in sync (via `IQueryProjectionService` against `AuthDbContext`) with `TenantMembershipCreatedEvent`/`TenantMembershipRemovedEvent` and the new role events, keyed by `$"{tenantId}:{externalUserId}"`, per `auth/authorization-lookup`.
5. Add `ITenantRoleAuthorizationService` (contract) to `Lewee.Application`, and its implementation in `Lewee.Auth.Application` querying the projection from step 4.
6. Add `IAdministratorRequest`/`ITenantRoleRequest` to `Lewee.Application.Mediation.Requests`, and `AdministratorAuthorizationBehavior`/`TenantRoleAuthorizationBehavior` to `Lewee.Application.Mediation.Behaviors`, wired via `AddPipelineBehaviors`'s `additionalBehaviors` parameter, per `application/administrator-authorization` and `application/tenant-role-authorization`.
7. Promote the reserved administrative tenant code from `AuthSeeder`'s private constant to a shared constant on `Lewee.Auth.Domain.Tenant` (or similar), used by both `AuthSeeder` and the new `IAdministratorRequest` check.
8. Add unit tests: `Lewee.Auth.Domain.Tests.Unit` (role definition/assignment/removal, idempotency, cross-tenant rejection), `Lewee.Auth.Application.Tests.Unit` (projection sync, `ITenantRoleAuthorizationService`), `Lewee.Application.Tests.Unit` (both behaviors, including the "no marker interface ⇒ unaffected" and "no authenticated caller ⇒ `Unauthenticated`" scenarios from the specs).
9. Run `dotnet build --configuration Release --nologo`, `dotnet test --filter "FullyQualifiedName!~Integration" --configuration Release --no-build --nologo`, and `dotnet format` to confirm no regressions.
10. (Deferred, tracked only) adopt `IAdministratorRequest`/`ITenantRoleRequest` on real Pizzeria commands/queries, and add the role-management commands/endpoints (Non-Goals) - both are separate follow-up changes under parent issue #87.

No rollback beyond standard EF Core migration `Down()` methods is planned; this is additive (new tables/columns), so no existing data is at risk.

## Open Questions

- Whether `Role` assignment on `TenantMembership` should support multiple roles per membership per tenant (this plan assumes yes, mirroring how a `User` can hold multiple `TenantMembership`s) - implementation can confirm this reading of issue #87 without changing the specs in this plan.
- The exact shape of the future role-management commands/endpoints (`DefineRoleCommand`, `AssignRoleCommand`, required permissions to call them) is deliberately left for later work (see Non-Goals); this plan only fixes the domain/lookup/pipeline shape needed to support it.
